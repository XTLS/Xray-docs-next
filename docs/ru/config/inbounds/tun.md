# TUN

Создает TUN-интерфейс. Трафик, направленный в этот интерфейс, обрабатывается Xray. В настоящее время поддерживаются Windows, Linux, macOS и FreeBSD.

На Android и iOS TUN FD должен передаваться внешним приложением через переменную окружения `XRAY_TUN_FD`, при этом для перенаправления трафика используется интерфейс, назначенный системой. Он не может запускаться самостоятельно и служит лишь способом для приложения передавать трафик в Xray.

На Linux эту переменную окружения можно опционально использовать для передачи TUN FD в некоторых облегченных или непривилегированных реализациях.

## InboundConfigurationObject

`InboundConfigurationObject` соответствует элементу `settings` в [`InboundObject`](../inbound.md).

```json
{
  "inbounds": [
    {
      // ...
      "protocol": "tun",
      // [!field focus]
      "settings": {
        "name": "utun10",
        "desc": "Wintun",
        "mtu": 1500,
        "gateway": ["10.0.0.1/16", "fc00::1/64"],
        "dns": ["1.1.1.1", "8.8.8.8"],
        "userLevel": 0,
        "autoSystemRoutingTable": ["0.0.0.0/0", "::/0"],
        "autoOutboundsInterface": "auto",
        "autoSystemDnsToGateway": false,
        "autoSystemWfpBlockLeak": ["dns", "misconfig"]
      }
    }
  ]
}
```

> `name`: string

Имя создаваемого TUN-интерфейса. По умолчанию `"utunN"`.

Где N — случайное число в диапазоне от 10 до 1024.

> `desc`: string

Описание имени сетевого интерфейса в Windows. По умолчанию `Wintun`. Эта строка объединяется со словом "Tunnel", образуя "xxx Tunnel".

В Windows можно использовать `route print` для просмотра подробной информации.

> `mtu`: number

Значение MTU интерфейса. По умолчанию `1500`.

> `gateway`: [string]

Список префиксов адресов, назначаемых TUN-интерфейсу, обычно отдельно для IPv4 и IPv6, например `"10.0.0.1/16"` и `"fc00::1/64"`.

Если параметр не задан, результат зависит от системы: в Linux Xray не назначает адресов; в Windows система сама назначает TUN-интерфейсу локальные адреса канала (IPv6 сразу, IPv4 из `169.254.0.0/16` через несколько секунд); в macOS и FreeBSD используется `169.254.10.1/30`. macOS и FreeBSD используют только первый IPv4-префикс.

> `dns`: [string]

Список DNS-серверов, назначаемых TUN-интерфейсу, например `"1.1.1.1"` и `"8.8.8.8"`.

Параметр действует только в Windows, где серверы назначаются TUN-интерфейсу. Windows отправляет запросы им, а также DNS-серверам других интерфейсов; `"dns"` в `autoSystemWfpBlockLeak` блокирует последние. Запросы к этим серверам идут через TUN-интерфейс, только если серверы входят в `gateway` или `autoSystemRoutingTable`. В Xray это обычный трафик на порт 53: правило маршрутизации может передать его [DNS-исходящему](../outbounds/dns.md), иначе он пересылается этим серверам, как любой другой трафик. Адреса TUN-интерфейса не регистрируются в DNS, а кэш DNS очищается при запуске и остановке TUN-интерфейса.

Если используется `autoOutboundsInterface`, DNS-сервер `localhost` в Xray обходит эти серверы (если только их не использует и другой интерфейс), так как его запросы к ним вернулись бы в TUN-интерфейс.

В Linux системный DNS не берется из этого параметра, см. `autoSystemDnsToGateway`; в macOS системный DNS не настраивается.

> `userLevel`: number

Уровень пользователя. Для соединения будет использоваться [локальная политика](../policy.md#levelpolicyobject), соответствующая этому уровню пользователя.

Значение userLevel соответствует значению `level` в [policy](../policy.md#policyobject). Если не указано, по умолчанию равно 0.

> `autoSystemRoutingTable`: [string]

Список целевых префиксов, которые Xray автоматически добавляет в системную таблицу маршрутизации, чтобы трафик направлялся в этот TUN-интерфейс. Каждый элемент задается в формате CIDR. Например, `"0.0.0.0/0"` означает весь IPv4-трафик, а `"::/0"` означает весь IPv6-трафик.

В настоящее время поддерживается на Windows, macOS и Linux. На FreeBSD таблицу маршрутизации необходимо настраивать вручную.

> `autoOutboundsInterface`: string

Автоматически привязывает исходящие соединения Xray к физическому сетевому интерфейсу, чтобы трафик, создаваемый самим Xray, не отправлялся обратно в TUN и не образовывал петлю.

Эквивалентно автоматической установке [sockopt](../transports/sockopt.md).interface для всех исходящих соединений (при этом дополнительно охватывает и некоторые запросы, для которых нельзя настроить параметры исходящего соединения, например различные локальные режимы встроенного DNS); может быть переопределено вручную заданным sockopt.

Значение по умолчанию — `null`, то есть параметр не задан. Можно указать конкретное имя интерфейса или `"auto"`, чтобы Xray выбрал его автоматически. Если задан `autoSystemRoutingTable`, но это поле явно не указано, Xray будет обрабатывать его как `"auto"`.

> `autoSystemDnsToGateway`: true | false

Этот параметр действует только в Linux. По умолчанию `false`.

Если параметр включен, Xray направляет системный резолвер systemd-resolved (через `resolvectl`) на TUN-интерфейс, чтобы системные DNS-запросы шли через Xray. Используется первый IPv4-адрес из `gateway` плюс один (например, `10.0.0.1/16` → `10.0.0.2`), а без IPv4 — первый IPv6-адрес плюс один (например, `fc00::1/64` → `fc00::2`); без `gateway` ничего не меняется. Адрес не берется из `dns`, иначе systemd-resolved опрашивал бы эти серверы напрямую, мимо TUN-интерфейса.

Запросы на этот адрес должен обрабатывать Xray, поэтому нужно правило маршрутизации, которое передает порт 53 этого входящего подключения [DNS-исходящему](../outbounds/dns.md). Перед изменением системного DNS Xray проверяет это и ничего не меняет, если такой запрос не дойдет до DNS-исходящего или если собственный [DNS](../dns.md) Xray может обращаться к системному резолверу (нет DNS-серверов или задан `localhost`), что привело бы к петле.

Нужен запущенный systemd-resolved версии 240 или новее, иначе системный DNS не меняется. При обычном завершении Xray настройка отменяется; если Xray был принудительно завершен (например, `SIGKILL`), выполните `resolvectl revert <интерфейс>`.

> `autoSystemWfpBlockLeak`: [string]

Этот параметр действует только в Windows. По умолчанию он пуст, то есть фильтры не добавляются.

Если задан `autoSystemRoutingTable`, Xray добавляет фильтры Windows Filtering Platform (WFP), которые не дают трафику других программ уходить мимо TUN-интерфейса; каждый вид выбирается значением в списке:

- `"dns"`: если задан `dns`, DNS (порт 53) может идти только через TUN-интерфейс или от самого Xray. Windows отправляет запросы DNS-серверам всех интерфейсов, каждому через его собственный интерфейс независимо от маршрутов, а другие программы обращаются к DNS-серверу в локальной сети (например, `192.168.1.1`, выданному DHCP) по более точному маршруту локальной сети, так что без этого такие серверы по-прежнему опрашивались бы мимо TUN. В Windows 11, Windows Server 2022 и новее эти запросы могут идти и по DNS over HTTPS или TLS, так что службе «DNS-клиент» (Dnscache) подключаться мимо TUN-интерфейса нельзя вовсе, кроме разрешения имён в локальной сети (LLMNR, mDNS). Поэтому серверы из `dns` должны входить в `gateway` или `autoSystemRoutingTable`, а DNS-серверы, к которым нужно обращаться напрямую, следует указывать в собственных настройках [DNS](../dns.md) Xray.
- `"misconfig"`: версия IP (IPv4 или IPv6), для которой в `autoSystemRoutingTable` нет маршрутов, блокируется в обоих направлениях, кроме самого Xray, loopback и того, что нужно Windows в локальном сегменте сети (DHCP, обнаружение соседей IPv6). Чтобы TUN-интерфейс передавал версию IP, адрес этой версии в `gateway` не нужен: без него Windows сама назначает ему локальный адрес канала (IPv6 сразу, IPv4 из `169.254.0.0/16` через несколько секунд).

Пока фильтры действуют, исходящие соединения самого Xray также обходят блокирующие правила брандмауэра Windows.

Фильтры удаляются при завершении Xray, даже аварийном. Если добавить их не удалось, TUN-интерфейс не запускается (в Windows 10 и новее; в более старых версиях только выводится предупреждение).

По умолчанию параметр пуст, так как фильтры мешают в некоторых случаях: с `"dns"` — локальный DNS-резолвер, используемый другими программами (например, на `127.0.0.1:53`), DNS другого VPN, виртуальные машины, NAT которых разрешает имена на хосте, или вход в captive portal; с `"misconfig"` — IPv4 или IPv6 в локальной сети, когда маршрутов этой версии в TUN-интерфейс нет. Без фильтров DNS может утекать, как описано выше. Чтобы намеренно не пускать версию IP в TUN-интерфейс и при этом блокировать утечки DNS, используйте только `["dns"]`.

## Советы по использованию

Если `autoSystemRoutingTable` не настроен, маршруты для направления трафика в созданный TUN-интерфейс по-прежнему нужно добавлять вручную, иначе он останется просто сетевым интерфейсом.

Если настроены `gateway`, `dns`, `autoSystemRoutingTable` и `autoOutboundsInterface`, Xray может автоматически выполнить часть системной настройки на поддерживаемых платформах. Если на вашей платформе такие автоматические настройки еще не реализованы, либо вам требуется более тонкая настройка маршрутизации, системную часть все равно придется настраивать вручную.

Если вы хотите проксировать только один или несколько процессов, будет очень полезна маршрутизация по имени процесса в системе маршрутизации Xray.

::: warning
Остерегайтесь возможных петель трафика (traffic loops). После настройки маршрутизации запросы, отправляемые Xray, могут быть направлены обратно в Xray и образовать петлю.
В первую очередь используйте `autoOutboundsInterface`, чтобы избежать этой проблемы. Если нужен ручной контроль, можно использовать `interface` в `sockopt` для привязки к реальному физическому сетевому интерфейсу. Команды `ipconfig` (Windows) и `ip a` (Linux) помогут найти имя нужного вам интерфейса.
Или используйте `sendThrough` для исходящих соединений. Он доступен непосредственно в OutboundObject и не имеет такой глубокой вложенности, как `sockOpt.interface`. Здесь необходимо использовать IP-адрес сетевой карты, например 192.168.1.2 (как видите, его недостатком является отсутствие автоматической поддержки dual-stack, пожалуйста, выбирайте в соответствии с фактически используемым IP для исходящего трафика).
:::
