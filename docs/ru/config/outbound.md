# Исходящие подключения

Исходящие подключения используются для отправки данных. Доступные протоколы см. в разделе [Исходящие протоколы](./outbounds/).

## OutboundObject

`OutboundObject` соответствует дочернему элементу поля `outbounds` в конфигурационном файле.

::: tip
Первый элемент в списке используется как основной исходящий узел.
Если совпадений с правилами маршрутизации нет или ни одно правило не сработало, трафик отправляется через основной исходящий узел.
:::

```json
{
  "outbounds": [
    {
      "sendThrough": "0.0.0.0",
      "protocol": "название протокола",
      "settings": {},
      "tag": "тег",
      "streamSettings": {},
      "targetStrategy": "AsIs"
    }
  ]
}
```

> `sendThrough`: address

IP-адрес, используемый для отправки данных.
Этот параметр используется, если на хосте настроено несколько IP-адресов.
Значение по умолчанию - `"0.0.0.0"`.

Разрешается указывать блок IPv6 CIDR (например, `114:514:1919:810::/64`).
Xray будет использовать случайный IP-адрес из этого блока для установления исходящих соединений.
Необходимо правильно настроить сетевое подключение, таблицу маршрутизации и параметры ядра, чтобы разрешить Xray привязываться к любому IP-адресу из этого блока.

Специальное значение `origin` — при использовании этого значения запросы будут отправляться с IP-адреса, через который было установлено соединение с локальной машиной.

Специальное значение `srcip` — при использовании этого значения запросы будут отправляться с исходного IP-адреса входящего соединения.

Например, если на машине есть целый блок IPv4-адресов `11.4.5.0/24` и прослушивается 0.0.0.0 (все IPv4 и IPv6 адреса на сетевой карте), и клиент подключается к локальной машине через `11.4.5.14`, то исходящие запросы также будут отправляться через `11.4.5.14`. Если же клиент использует `11.4.5.10` для подключения к локальной машине, то исходящие запросы будут отправляться через `11.4.5.10`. То же самое относится и к случаям, когда на машине есть целый блок/несколько IPv6-адресов.

Как и в описании для `inbound`, из-за особенностей `UDP` как протокола без установления соединения, `Xray` не может определить исходный целевой `IP`-адрес запроса, поступающего в ядро (например, в рамках одного и того же `QUIC`-соединения он может даже меняться), поэтому эта функция не может работать.

> `protocol`: "blackhole" | "dns" | "freedom" | "http" | "loopback" | "shadowsocks" | "socks" | "trojan" | "vless" | "vmess" | "hysteria" | "wireguard" | "masque"

Название протокола соединения. Список доступных протоколов см. в разделе [Исходящие протоколы](./outbounds/) в меню слева.

> `settings`: OutboundConfigurationObject

Конкретные настройки зависят от протокола.
См. описание `OutboundConfigurationObject` для каждого протокола.
Для VLESS и VMess здесь же настраиваются [Multiplex и XUDP](#muxobject).

> `tag`: string

Тег этого исходящего подключения, используемый для идентификации этого подключения в других настройках.

::: danger
Если это поле не пустое, его значение должно быть **уникальным** среди всех тегов.
:::

> `streamSettings`: [StreamSettingsObject](./transport.md)

Конфигурация транспорта для этого исходящего подключения.

> `targetStrategy`: "AsIs" | "UseIP" | "UseIPv6v4" | "UseIPv6" | "UseIPv4v6" | "UseIPv4" | "ForceIP" | "ForceIPv6v4" | "ForceIPv6" | "ForceIPv4v6" | "ForceIPv4"

Применяется к исходящим подключениям, кроме Freedom. Определяет, нужно ли локально разрешать целевое доменное имя проксируемого запроса в IP и какую стратегию разрешения использовать.

Значение по умолчанию — `AsIs`: целевое доменное имя передается на удаленный сервер без изменений. Смысл стратегий в основном совпадает с `domainStrategy` в [Sockopt](./transports/sockopt.md#sockoptobject).

::: tip
Здесь контролируются **проксируемые запросы**. Если адресом исходящего прокси-сервера является доменное имя, и для этого домена необходимо выбрать стратегию разрешения, следует настроить `domainStrategy` в [Sockopt](./transports/sockopt.md#sockoptobject).

Стратегию разрешения доменных имен для Freedom также следует задавать через `sockopt.domainStrategy`.
:::

### Multiplex и XUDP

Multiplex (Mux) позволяет клиенту передавать несколько потоков через одно соединение с сервером. XUDP передаёт UDP-пакеты через Multiplex.

Настройка доступна для исходящих [VLESS](./outbounds/vless.md) и [VMess](./outbounds/vmess.md). В конфигурации клиента добавьте `multiplex` внутрь `settings`, рядом с адресом сервера и учётными данными. На сервере отдельная настройка Multiplex не нужна.

В этом фрагменте клиент может передавать до восьми потоков одновременно через одно соединение.

```json
{
  "settings": {
    "multiplex": {
      "concurrency": 8
    }
  }
}
```

#### Что указать в `multiplex`

В примерах ниже показано содержимое объекта `multiplex`.

- **TCP и UDP через одни и те же соединения.** `{"concurrency": 8}`
- **Только UDP через Multiplex.** `{"xudpConcurrency": 8}`. Для TCP Xray открывает обычные соединения.
- **TCP и UDP через разные соединения Multiplex.** `{"concurrency": 8, "xudpConcurrency": 16}`
- **Без пулов Multiplex.** Удалите `multiplex` или оставьте пустой объект `{}`. Xray будет обрабатывать TCP и UDP обычным способом для выбранного протокола. Нулевое значение любого из двух параметров действует так же, как пропущенное.

Для [VLESS с Vision и XDrive](./outbounds/vless.md#multiplex) есть отдельные правила.

#### Сколько потоков помещается в одно соединение

`concurrency` задаёт лимит одновременно активных потоков в общем пуле, а `xudpConcurrency` — в отдельном пуле UDP. Для включённого пула указывайте от **1 до 1024**. При лимите `8` девятый одновременный поток Xray направит через другое соединение.

Через одно соединение можно пропустить не более **1024 потоков за всё время его работы**, включая уже завершённые. Когда этот лимит исчерпан, Xray направляет новые потоки через другие соединения, а текущим даёт завершиться.

#### Что происходит с UDP на порту 443

Если UDP идёт через Multiplex, по умолчанию Xray отклоняет пакеты на порт `443`. Такой порт часто используется для QUIC. Задайте `xudpProxyUDP443` внутри `multiplex`, если хотите другое поведение.

- `reject` — отклонять UDP на порт `443`.
- `allow` — передавать его через Multiplex.
- `skip` — передавать его обычным способом для этого протокола. При `flow: "xtls-rprx-vision"` VLESS на обычном пути отклоняет UDP на порт `443`.

#### Как перейти со старого `mux`

Удалите `mux` из исходящего подключения. Если он был включён и вы хотите сохранить Multiplex, добавьте `settings.multiplex` для VLESS или VMess и выберите режим выше. Например, если раньше было `"mux": {"enabled": true}` без дополнительных параметров, для общего пула укажите `"multiplex": {"concurrency": 8}` внутри `settings`.

Если в конфигурации остался старый `mux`, Xray выводит предупреждение в консоль при загрузке и игнорирует этот ключ. Если указаны оба ключа, действуют только параметры в `settings.multiplex`. Для остальных исходящих протоколов Multiplex недоступен.

Отрицательные значения в новом объекте вызывают ошибку загрузки. Старое `xudpConcurrency: -1` исключало UDP из общего пула. Если в новом объекте задать `0`, отдельный пул UDP отключится, а UDP сможет идти через общий пул, если он включён.

При добавлении исходящего подключения через API передавайте `multiplex` в конфигурации VLESS или VMess. Старое поле `SenderConfig.multiplex_settings` игнорируется. Запрос с отрицательными значениями отклоняется.

См. [прежнее описание `mux`](https://github.com/XTLS/Xray-docs-next/blob/0caf7ea80eb491eb1d6d7fc8cc7c347f55198e22/docs/ru/config/outbound.md#muxobject) для старых сборок, [Multiplex поверх XHTTP](./transports/xhttp.md#multiplex) и [описание кадров Mux.Cool](../development/protocols/muxcool.md).
